# 项目深度学习

把仓库当作待考证的系统，而不是待概括的文件集合。目标是建立一张从业务目标到可安全修改代码的**证据地图**：每个重要结论都能回到源码、配置、测试、文档或 Git 历史。

## 学习模式

根据用户目标选择最窄的模式；没有指定时使用全景模式。

- **全景模式**：覆盖项目全貌和本 skill 的全部完成条件。
- **专题模式**：围绕一个模块、流程或质量属性深挖，同时交代它在全局中的位置。
- **入门模式**：压缩实现细节，强化术语、入口、主流程、调试方式和首个安全修改任务。
- **变更准备模式**：以用户准备修改的功能为中心，追踪边界、依赖、约束、测试和风险。

## 证据纪律

使用以下标签区分确定性，不把推断写成事实：

- **已确认**：由当前源码、配置、测试或可复现命令直接证明。
- **交叉验证**：至少两类独立证据一致，例如实现与测试、配置与部署清单。
- **推断**：证据支持但仓库没有明确声明；写出推理链。
- **待确认**：证据缺失、互相冲突或需要运行环境才能验证。
- **历史背景**：来自 Git 历史；说明它解释的是过去决策，不自动代表当前意图。

引用结论时给出仓库相对路径，关键实现尽量带行号或符号名。文档与代码冲突时并列呈现两方证据，并以当前可执行行为描述现状。

## 工作流

### 1. 建立调查基线

确认仓库根目录、当前分支和工作区状态。读取适用的 `AGENTS.md`、根级 README、构建清单、依赖清单、锁文件、容器与 CI 配置；只记录与理解项目相关的信息，不读取凭据内容。

识别单仓、多包仓、服务集合、库、CLI 或混合形态，并列出主要语言、框架、包管理器和构建系统。完成标准：能说明“这是什么类型的项目、如何被组织、哪些规则约束后续调查”。

### 2. 绘制仓库地图

先按目录、清单和入口文件建立粗粒度地图，再选择代表性文件阅读。区分业务源码、平台适配、测试、脚本、生成物、第三方代码、文档和基础设施；不要用逐文件罗列代替模块理解。

为每个主要模块记录：职责、公开入口、拥有的数据、直接依赖、主要调用者、运行形态和测试位置。项目较大时，可让多个探索 agent 分别调查业务、架构/运行时、工程质量与历史，主 agent 负责消除重复和矛盾。完成标准：每个一层主要目录和运行单元都有归类，未理解区域被明确标记。

### 3. 建立领域与架构模型

从 README、用户入口、类型名、接口、数据模型、测试用例和错误信息中提取项目目标、参与者、核心能力、业务术语、不变量与生命周期。随后识别模块边界、公开接口、适配器、共享内核和外部系统。

检查依赖方向是否符合声明架构，并区分“设计边界”和“代码实际耦合”。需要完整问题集时读取 [调查清单](references/investigation-checklist.md)。完成标准：能用项目自己的术语解释系统解决什么问题，以及每个核心模块为何存在、允许依赖谁。

### 4. 追踪真实执行路径

从真实入口向内追踪，不根据目录名猜测运行方式。至少选择最重要的成功路径；全景模式还应选择一个失败、异步、后台或持久化路径（项目确实存在时）。每条路径记录：

1. 进程、请求、命令、事件或作业入口。
2. 配置加载、依赖装配和生命周期初始化。
3. 编排层与核心业务决策。
4. 状态变化、数据转换和持久化边界。
5. 外部 I/O、错误传播、重试与清理。
6. 日志、指标、追踪或其他可观察结果。

用调用链和数据形态说明流程，而不是只列函数名。完成标准：读者能预测一次输入如何变成输出，以及关键失败会在哪里被发现和处理。

### 5. 找到修改杠杆点

识别决定行为的关键类、函数、接口、配置项和数据结构。解释它们的调用约束、不变量、扩展点、错误语义和兼容性要求；同时记录设计模式、工程实践及可见的技术取舍。

用测试定位稳定接口，用配置定位部署差异，用调用方定位真实契约。完成标准：针对一个典型需求，能指出应修改的位置、不应穿透的边界、必须同步检查的调用方和最小验证集合。

### 6. 审计工程系统与历史

调查测试分层、构建发布、部署拓扑、可观测性、安全边界和性能策略。仅在当前证据解释不了异常设计时查看相关文件的 Git 历史、提交和 blame；把兼容层、重复实现、命名偏差、全局状态、特殊脚本等分为“有证据的历史包袱”和“仍需确认的可疑约定”。

保持只读调查。启动服务、连接外部系统、执行迁移、写数据库或运行高成本任务前，遵循项目授权规则。完成标准：每个质量领域都有证据、明确的“不适用”，或具体知识缺口。

### 7. 交叉验证

使用文档、实现、配置、测试和历史相互校验。优先运行安全、范围最小的只读检查或现有测试来验证关键假设；命令不可运行时记录原因，不以静态阅读冒充运行验证。

专门检查以下漂移：文档与代码、接口与调用方、配置默认值与部署覆盖、数据结构与序列化格式、架构声明与实际依赖、测试预期与生产路径。完成标准：重要结论均有证据等级，冲突和未知项没有被静默消解。

### 8. 形成学习成果

按 [报告模板](references/report-template.md) 输出。默认在回复中给出结果；只有用户明确要求持久化时，才写入用户指定位置或仓库已有的项目知识目录。

学习路线必须由实际依赖关系驱动，而不是通用课程表。每一阶段包含：要回答的问题、必读入口、一次可观察运行或测试、一个小型修改练习、完成判据。最后给出首个低风险任务及其验证命令。完成标准：读者不仅“看懂”，还能沿现有边界完成一次小修改并验证没有破坏契约。

## 完成门槛

全景模式只有同时满足以下条件才算完成：

- 项目目标、业务领域、核心概念与术语已建立。
- 技术栈、目录结构和主要模块职责已覆盖。
- 系统架构、模块边界、公开接口和依赖方向已说明。
- 启动过程、至少两条代表性运行路径和数据流已追踪；不存在第二条路径时说明原因。
- 关键类、函数、配置和数据结构已关联到实际流程。
- 设计模式、工程实践和主要技术取舍均有证据。
- 测试、部署、可观测性、安全和性能均有结论或明确缺口。
- 项目特有约定与历史包袱已区分事实、推断和历史背景。
- 学习路线以“能够独立完成并验证一个小修改”为终点。
- 所有关键结论可追溯，所有冲突、未覆盖区域和运行验证缺口已列出。
