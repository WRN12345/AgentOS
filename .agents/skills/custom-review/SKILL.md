---


请对当前 Git 分支的所有修改进行一次严格、只读的代码审查，重点寻找真实、可触发、值得开发者修复的问题。

## 一、审查目标

审查当前分支相对于基准分支引入的变更，包括：

1. 当前分支已经提交的修改。
2. Git 暂存区中的修改。
3. 工作区尚未暂存的修改。
4. 与本次功能相关的未跟踪文件。

默认基准分支为 `main`。如果本地不存在 `main`，优先使用当前分支配置的 upstream，再按以下顺序查找可用基准：

1. 当前分支配置的 upstream
2. `origin/main`
3. `master`
4. `origin/master`

不得将当前分支本身作为基准分支。若 upstream 指向当前分支或无法解析，跳过它并继续查找。

不得执行 `git fetch`、`git pull`、`git checkout`、`git switch`、`git reset`、`git clean`、`git stash` 或任何会修改仓库状态的命令。

## 二、只读检查流程

首先执行只读检查：

```bash
git branch --show-current
git status --short
git remote -v
git log --oneline --decorate -20
```

确定基准分支后，通过 merge-base 获取准确审查起点：

```bash
git merge-base HEAD <BASE_REF>
```

然后检查：

```bash
git diff --stat <BASE_SHA>...HEAD
git diff <BASE_SHA>...HEAD
git diff --cached
git diff
git ls-files --others --exclude-standard
```

不要只阅读 diff。对于每一处修改，还必须阅读：

- 修改函数或类型的完整实现。
- 直接调用方和被调用方。
- 相关接口、数据结构和配置。
- 相关测试。
- 涉及共享状态时的读写路径。
- 涉及异步操作时的启动、等待、取消及清理路径。
- 涉及错误处理时的异常传播和恢复路径。

只审查，不要修改任何文件，不要运行格式化器，不要创建 commit，不要推送代码。

如果需要运行测试，只能运行已经存在且确认安全的本地测试命令；不得安装依赖、修改配置、连接生产环境或使用真实凭据。运行测试后重新执行 `git status --short`，确认没有产生意外修改。

## 三、重点检查内容

### 1. 逻辑正确性

检查：

- 条件判断是否相反、遗漏或永远无法成立。
- 循环边界、数组索引和 off-by-one 错误。
- 空值、空集合、零值、负数、溢出及异常输入。
- 状态是否可能进入不一致或不可恢复的状态。
- 返回值是否被错误解释或忽略。
- 错误分支是否错误地继续执行。
- 成功路径和失败路径是否都正确清理资源。
- 重试逻辑是否会重复产生副作用。
- 分页、排序、过滤、缓存和去重逻辑是否正确。
- 修改是否破坏现有接口或调用方假设。
- 实现是否偏离任务需求或现有业务规则。

### 2. 并发和竞态问题

重点寻找：

- 多线程、协程或异步任务对共享状态的无保护读写。
- check-then-act、TOCTOU 竞态。
- 非原子的读取—修改—写入操作。
- 锁缺失、锁粒度错误或锁顺序不一致。
- 死锁、活锁、饥饿或重复等待。
- 在持锁状态下执行阻塞 I/O 或长时间操作。
- 异步任务未等待、重复启动或提前退出。
- 任务取消后仍然修改状态。
- 超时后后台操作仍然继续产生副作用。
- 回调、事件监听器或订阅没有正确注销。
- Channel、Queue、Future、Promise 使用不正确。
- 缓存初始化和单例初始化竞态。
- 并发重试导致重复写入或重复请求。
- 缺乏幂等性导致重复消费或重复提交。
- 数据库事务边界与业务原子性不一致。
- 数据库读取后再更新产生丢失更新。
- 文件写入、临时文件替换或重命名不具备原子性。

不要仅因为代码使用异步或共享变量就报告竞态。必须说明至少两个操作如何交错，并展示能够触发错误的执行顺序。

### 3. 错误处理和可靠性

检查：

- 异常被吞掉或只记录后继续运行。
- 返回错误但调用方没有处理。
- 错误类型或状态码不正确。
- 部分成功后没有回滚。
- 超时、重试和退避配置不合理。
- 对不可重试操作进行重试。
- 重试可能重复写入、扣费或发送消息。
- 网络连接、文件句柄、锁、事务或进程没有释放。
- 清理逻辑只存在于成功路径。
- 错误日志泄露凭据或隐私数据。
- 失败后返回看似成功的结果。
- 降级或 fallback 隐藏真实故障。

### 4. 数据一致性

检查：

- 数据库写入是否具有正确事务边界。
- 多步操作中途失败是否会留下部分状态。
- 缓存和持久化数据是否可能不一致。
- schema、序列化格式或字段语义是否兼容旧数据。
- 时区、日期、精度和单位是否一致。
- 去重键、唯一约束和幂等键是否正确。
- 删除、更新和关联操作是否可能误伤其他数据。

### 5. 安全问题

检查：

- 命令注入、SQL 注入、路径穿越和模板注入。
- 用户输入是否进入 shell、SQL、文件路径或 URL。
- 认证和权限检查是否遗漏或顺序错误。
- 敏感操作是否存在越权可能。
- API Key、Token、密码或个人数据是否进入日志。
- 服务端请求伪造（SSRF）。
- 不安全反序列化。
- 临时文件权限或文件覆盖问题。
- 外部返回内容是否被当作可信指令执行。
- 默认配置是否意外暴露服务或调试接口。

### 6. 生命周期和资源管理

检查：

- 文件、连接、锁、事务、进程、线程是否正确关闭。
- 早退和异常路径是否执行清理。
- 定时器、监听器、后台任务是否泄漏。
- 对象销毁后是否仍存在异步回调。
- 应用关闭时是否正确停止后台任务。
- 初始化失败是否留下半初始化状态。

### 7. 测试质量

检查：

- 本次修改是否缺少关键测试。
- 测试是否真正覆盖新行为，而不仅是执行代码。
- 是否覆盖失败路径、边界条件和并发场景。
- 测试是否因为 mock 过度而无法发现真实问题。
- 测试是否存在时间敏感、随机失败或顺序依赖。
- 测试断言是否过弱。
- 实现与测试是否共同误解了业务要求。

测试缺失只有在可能掩盖具体、可描述的回归风险时才报告。只有当缺少测试会使该风险无法被发现时，才能报告测试缺口；不得仅因修改没有新增测试就报告问题。不要把“可以增加更多测试”作为泛泛建议。

## 四、问题认定标准

只报告满足以下条件的问题：

1. 问题由当前分支的修改引入，或者当前修改明显放大了既有问题。
2. 存在具体、合理的触发条件。
3. 能说明受影响的代码路径和实际后果。
4. 开发者看到后大概率会愿意修复。
5. 不是纯粹的代码风格、个人偏好或无证据猜测。

对于仓库原本就存在、与本次修改无关的问题，不要混入主要 Findings。可以放到“既有问题”部分，并明确说明不是本分支引入。

如果证据不足，不要断言存在 Bug。将其放在“待确认问题”中，并说明缺少什么证据。确认的问题必须具有高或中置信度；低置信度问题只能放入“待确认问题”，不得放入 Findings。

## 五、严重等级

使用以下等级：

- `P0 致命`：会造成大范围数据丢失、严重安全事故、生产服务完全不可用。
- `P1 严重`：在合理条件下导致核心功能错误、死锁、数据损坏、权限绕过或持续服务故障。
- `P2 一般`：影响部分功能、特定边界情况、可靠性或可维护性，应当修复。
- `P3 较低`：影响较小但明确存在，修复成本合理。
- 不报告纯格式、命名和主观风格建议。

## 六、每个问题的输出格式

每个问题必须包含：

### [P0/P1/P2/P3] 简短、明确的问题标题

- 文件：`path/to/file.ext`
- 行号：尽量给出最小且准确的行号范围
- 置信度：高 / 中 / 低
- 问题：具体哪段逻辑不正确
- 触发条件：什么输入、状态或并发顺序会触发
- 执行路径：从入口到错误位置的关键调用链
- 影响：会产生什么可观察后果
- 证据：代码、测试或可复现步骤如何证明
- 修复建议：给出最小修复方向，不要直接修改代码

竞态问题还必须给出类似下面的交错顺序：

```text
T1：读取状态 A
T2：读取状态 A
T1：写入状态 B
T2：基于旧状态 A 写入状态 C
结果：T1 的更新丢失
```

## 八、禁止事项

- 不得修改代码。
- 不得自动修复问题。
- 不得创建或删除文件。
- 不得切换分支。
- 不得修改 Git 暂存区。
- 不得创建 commit。
- 不得执行 push、pull、fetch、merge 或 rebase。
- 不得删除或覆盖用户修改。
- 不得读取或输出 API Key、Token、密码和 `.env` 的完整内容。
- 不得读取 `.env`、密钥文件、凭据目录或其他敏感文件的完整内容。若需要判断其是否被引用，只查看文件名、引用位置或脱敏后的必要片段。
- 不得把单纯的代码风格偏好报告成 Bug。
- 不得报告无法说明触发路径的问题。
- 不得因为看到可疑代码就直接断言存在竞态。
- 不得用“可能有问题”代替具体技术分析。

现在开始只读审查。先确定当前分支、基准分支和完整变更范围，然后逐文件阅读修改及其上下文。
