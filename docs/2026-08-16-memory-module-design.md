参考：Hermes Agent 的分层记忆设计（四层记忆 + 闭环学习），已按 AgentOS 的团队协作场景改造

## 1. 要解决什么问题

现在系统里的 Agent 在拆解需求、分配任务时，每次只能临时查数据库里现有的信息（成员技能标签、当前负载）。它看不到三样东西：

1. **项目资料**：每个项目沉淀的文档（markdown、PDF、Word）和图片等资料，目前传上来就躺在那里，没有任何地方会读它们的内容。
2. **成员的"历史表现"**：某人过去做过哪些类型的任务、完成得怎么样、是否按时。现在只有静态的技能标签，没有事实依据。
3. **项目自己的"经验"**：上次类似的需求是怎么拆的、分配给谁、结果如何、踩过什么坑。这些经验现在随着每次运行结束就消散了，Agent 永远是"第一天上班"。

记忆模块就是把这三样补上。核心思想（参考 Hermes）：**Agent 既是记忆的使用者，也是记忆的生产者**——它工作中发现值得记住的东西会主动提议记下来，任务完成后会自动沉淀经验，于是系统越用越懂这个项目。

## 2. 整体思路：四层记忆

```
┌────────────────────────────────────────────────────────┐
│                      记忆模块                            │
│                                                         │
│  ① 项目记忆        ② 团队记忆        ③ 项目核心记忆      │
│  项目文档/资料      成员完成统计       少量高价值条目：     │
│  全量内容可检索     + 负责人档案      约定/决策/教训       │
│  （人上传）        （自动算+人写）    （Agent 提议，人确认）│
│                                                         │
│  ④ 历史与经验                                            │
│  历次拆解/分配记录、已完成工作项的结论可检索；              │
│  任务结束后自动沉淀"经验套路"                             │
│  （系统自动积累）                                         │
│                                                         │
│  两个消费者：                                             │
│  ❶ Agent 拆解/分配时自动参考（③常驻注入，①②④按需检索）    │
│  ❷ 团队成员在知识库页面提问                               │
└────────────────────────────────────────────────────────┘
```

各层分工一句话：

| 层 | 类比人的什么 | 谁生产 | 怎么用 |
|---|---|---|---|
| ① 项目记忆 | 桌上的资料堆 | 人上传文档 | 按需检索 |
| ② 团队记忆 | 对同事的了解 | 系统自动算 + 负责人写 | 分配时参考 |
| ③ 项目核心记忆 | 脑子里的关键常识 | Agent 提议、负责人确认 | 每次运行常驻注入 |
| ④ 历史与经验 | 工作经历和套路 | 系统自动积累 | 按需检索 + 自动沉淀 |

**多项目归属**（多项目改造已在 feat/multiproject 分支落地，本节按现状修订）：

- **项目级记忆（①③④）**：所有记忆数据从第一天起就带 `project_id`，查询时严格按项目隔离，遵循分支已有规约——请求经 `X-Project-Id` 解析项目上下文，header 越权（携带自己不是成员的项目）返回 403，对象越权（访问他项目所属对象）返回 404，并纳入多项目测试接缝的行为矩阵（双项目 fixture 下验证隔离与越权）。
- **全局基础设施**：embedding 模型、索引管道、worker 任务为全平台共用的一套设施，不属任何项目，靠 `project_id` + 类型字段区分数据。
- **唯一例外——成员文字档案（②的一部分）**：跨项目可见，随人走、不挂项目，详见第 7 节。

## 3. 项目记忆：文档怎么进来

**不上新上传入口**，复用现有的文件上传功能（已有权限控制、去重、审计）。流程：

1. 用户像现在一样上传文件；
2. **上传即入库**：文件自动进入索引队列，系统后台读取内容、切块、存入可检索的索引，不需要任何额外操作；
3. 读不出内容的格式（zip、图片等）照常存储，状态标为"未索引"，不影响其他文件。

**文件不可删除，只支持版本变更**：

- 知识库里的文档不提供删除入口，避免误删造成资料丢失和检索结果悬空；
- 同名文档重新上传 = 生成一个新版本，旧版本保留、可查看历史；
- 检索和问答永远只命中**最新版本**的内容，旧版本仅用于人工追溯；
- **严格不可删除**（2026-08-21 确认）：不设任何删除/下架例外，admin 也不例外。误传敏感文件的应急处理由运维 SOP 兜底（数据库层面对该版本做下架操作并记录），不作为产品功能。

## 4. 支持哪些格式

| 格式 | 本期支持 | 说明 |
|---|---|---|
| Markdown / txt | ✅ | 直接读内容 |
| PDF（文字型） | ✅ | 用解析库提取文字 |
| Word（.docx） | ✅ | 上传白名单要加上 .docx |
| 图片（png/jpg） | ❌ 后置 | 只存储，不读内容。后续可用 OCR 或视觉模型识别 |
| 扫描件 PDF | ❌ 后置 | 本质是图片，同样后置 |
| zip 等 | ❌ | 不读内容，标记"未索引" |

解析失败的文件（比如损坏的 PDF）标记为"索引失败"，不阻塞其他文件。

## 5. 检索是怎么工作的（原理简述）

不看懂这一节也不影响使用，供参考：

- 内容被切成若干**小块**（比如每块几百字，按文章结构切，不切断句子段落）。
- 每个小块通过一个 **embedding 模型**（本地 Ollama 跑 qwen3-embedding）转成一串数字（"向量"），这串数字代表这段文字的语义。
- 提问时，问题也被转成数字，然后找出"数字最接近"的那些内容块——意思就是语义上最相关的段落。即使用词不一样也能命中（比如问"怎么部署"，能命中写"发布步骤"的段落）。
- 向量存在 PostgreSQL 里（启用 pgvector 扩展，换一个官方数据库镜像即可），不引入新的服务。
- 文档、成员档案、历史记录、经验条目**共用同一套索引管道**，用"类型"字段区分，检索时可按类型过滤。

## 6. 索引进度可见

每份进入知识库的文件有一个状态，前端可见：

- `待处理` → `索引中` → `已索引`（可检索）/ `失败`（可重试）/ `未索引`（格式不支持读内容）

索引由后台 worker 异步执行（复用现有 Redis 队列），上传操作不会被拖慢。

## 7. 团队记忆：装什么

分两部分：

**① 历史完成统计（自动算，不需要任何人维护）**

从现有工作项数据自动计算每个成员的：

- 在各类技能标签下完成过多少任务
- 按时完成率
- 当前和近期的负载情况

**统计口径**（2026-08-21 确认）：宽口径——分子为"不晚于最终截止时间完成"的已完成项，分母为所有已完成项（取消/转交不计入）；展示时附样本量 n，n 过小时标注"样本不足"。

**成员离职/停用**（2026-08-21 确认）：档案与统计保留（项目历史检索需要"上次是谁做的"这一事实），标记为停用，不再进入分配候选。

**按项目分开计算和展示**（已确认决策）：成员的个人技能和熟悉板块是在具体项目中充实的，且项目内容之间必须保持隔离。因此统计严格项目内——在 A 项目做分配时只看该成员在 A 项目的历史表现；存储上统计记录带 `project_id`。代价是新项目冷启动时成员暂无历史数据，可接受。

Agent 分配任务时，除了"他会什么"（技能标签），还能看到"他在本项目做过什么、做得怎么样"（事实记录）。

**② 成员文字档案（负责人维护）**

自由文本，记录统计体现不出来的信息，比如"某人对支付模块的历史包袱很熟""某人擅长带新人"。

- **跨项目可见**（已确认决策）：档案**随人走**，以成员为单位全局存储、不挂项目。任何项目的负责人在做分配决策时都能检索到该成员的档案——一个人的特质不因换了项目而改变。
- **谁写**：负责人（leader/admin）。理由是这些内容主要服务于分配决策，而分配是负责人做的；成员自评容易夸大。档案跨项目可见后，编辑权默认规则：**该成员所属任一项目的负责人均可编辑**（细则见第 15 节待定项）。
- **生效**：写完直接生效，不走确认流程。
- **可见性**（2026-08-21 确认）：遵循第 12 节"项目内全员可见"原则，**被评价的成员本人也能看到自己的档案**，不做暗箱评价。
- 这些档案同样进入索引，可以被检索到；作为项目级隔离的唯一例外，检索层对档案类型单独放行跨项目命中——但**仅限负责人查询和 Agent 分配环节**两个场景（2026-08-21 确认），普通成员的问答检索不命中他项目无关人员的档案，详见第 16 节。

## 8. 项目核心记忆：Agent 主动记，人把关

这是参考 Hermes `MEMORY.md` 的一层：每个项目有一份**条目式的核心笔记**，记录少量高价值信息——技术约定（"本项目禁用递归查询"）、关键决策（"支付模块最终决定走独立服务"）、踩坑教训（"改 X 表结构一定要同步改 Y"）。

规则：

- **谁写**：Agent 在工作中判断"这个值得记住"时，提议一条记忆（新增/修改/作废）；**负责人确认后才生效**——复用现有的 Agent 建议审批模式，守住"Agent 不直接改数据"的护栏。负责人也可以直接手写条目。
- **提议会过期**（2026-08-21 确认）：提议挂起超过 7 天无人确认自动标记"已过期"，不再占用待确认列表；Agent 认为仍重要可重新提议。防止提议无限积压。
- **有容量预算**：每个项目的核心记忆设总量上限（建议 4000 字符左右，几十条）。快满时 Agent 会提议整合精简（合并过时/重复的条目），同样经负责人确认。容量预算逼大家只留真正重要的，而不是什么都往里堆。
- **怎么用**：每次 Agent 拆解/分配任务时，核心记忆**全量注入**上下文（因为量小，成本低），保证这些关键常识永远在场。
- 可见性：项目成员都能看，能看到每条是谁提的、谁确认的、什么时候生效的。
- **组织级预留**（已确认决策）：存储模型上为核心记忆条目预留归属字段（可挂项目，也可标记为"组织级"——全团队通用的技术约定/规范，所有项目检索时都会命中）。**本期只实现项目级**，组织级核心记忆留待后续启用，但表结构不为此返工。
- **冷启动**（2026-08-21 确认）：新项目没有历史积累时，负责人可手写几条"种子记忆"（技术栈、基本约定）让 Agent 起步不抓瞎；检索结果少时前端如实标注"本项目积累尚少"，不假装有记忆。

## 9. 历史检索：让"上次是怎么做的"可查

把系统运行中自然产生的记录也变成可检索的记忆：

- **历次需求拆解/分配的记录**：输入的需求、拆出的工作项、推荐的分配、最终被采纳的情况。
- **已完成工作项的结论**：做了什么、验收结果、评审意见。

这些内容在完成时自动进入索引（异步，不拖慢主流程）。之后：

- Agent 拆解新需求时，可以检索"以前类似的需求是怎么拆的、分给谁、结果如何"作为参考；
- 团队成员也可以在知识库页面直接问"上次支付相关的需求是怎么拆的？"

## 10. 闭环沉淀：任务结束后自动总结经验

这是"越用越懂你"的关键一环，参考 Hermes 的闭环学习：

- **触发时机**：工作项完成、或一次需求拆解的建议被采纳并执行完后，后台自动跑一个"总结任务"（异步 worker）。
- **做什么**：让模型回看这次过程，提炼可复用的经验，比如"这类包含导入功能的需求，上次拆成了 4 个工作项，后端占比最大""改报表模块时总要同步更新导出服务"。
- **产出物**：经验总结**不直接生效**，而是自动生成一条"核心记忆提议"，走第 8 节同一个负责人确认通道。确认后进入核心记忆，下次拆解分配时自动在场。
- 这样闭环沉淀不需要单独的存储和审批机制，复用核心记忆的整套设施，实现最简单。

## 11. 两个消费者怎么用记忆

**① Agent 拆解/分配任务时自动参考**

每次运行时，Agent 的上下文这样装配：

| 来源 | 方式 |
|---|---|
| ③ 项目核心记忆 | 全量常驻注入（量小） |
| ① 项目文档 | 按需求内容检索相关片段 |
| ④ 历史与经验 | 检索类似的拆解/分配记录 |
| ② 成员统计 + 档案 | 分配环节查询/检索 |

- **红线不变**：记忆只是 Agent 的"参考阅读材料"，Agent 依然只能产出建议，由人确认后才生效。Agent 写记忆也必须走确认通道。记忆内容不会直接改变任何业务数据。

**② 知识库问答页面（新前端页面）**

- 一个独立页面，像聊天一样提问："我们的部署流程是什么？"
- 系统返回答案，**并列出答案依据**（出自哪个文件的哪一段 / 哪条核心记忆 / 哪次历史记录），点击可查看原文。
- 给出依据是为了可验证——用户能确认答案不是编的，这是知识库被信任的基础。
- **查不到就明说**（2026-08-21 确认）：检索结果相似度低于阈值时不生成回答，直接告知"知识库里没有找到相关内容"，并列出最接近的几条线索供人工判断。一次被抓住编答案，知识库的信任就归零，宁拒答不编造。
- 本期为"一问一答"，多轮对话和打字机式的流式输出后置。

## 12. 权限

- 所有记忆内容对**项目内所有在职成员**可见，大家都能问、都能看。
- 不同项目之间严格隔离，A 项目的成员绝对检索不到 B 项目的内容。**唯一例外**：成员文字档案跨项目可见（见第 7 节）。
- 检索层直接做权限控制（不是只靠下载接口挡），Agent 检索和问答页面走同一条带权限校验的路径。
- **全局 admin**（多项目改造后 admin 是全局角色、不再是项目成员）：对各项目记忆内容**只读查看**，用于监督和审计；不参与核心记忆提议的确认，不能编辑成员档案（除非他在该项目同时是 leader）。
- 核心记忆的"写"（确认提议、手写条目、整合精简）仅负责人可操作。
- **审计**（2026-08-21 确认）：写操作全部纳入现有审计域——核心记忆提议/确认/整合、成员档案创建与编辑、文档版本上传；检索与问答查询不审计（避免"提问被记录"抑制使用）。
  2026-08-24 修订：问答历史按人落库（`qa_history`，仅提问者本人可见，负责人/admin 也看不到他人历史），这是用户自己的使用记录、不属于审计域；"审计域不记录提问"原则不变。

## 13. 涉及的技术改动一览

| 改动 | 内容 |
|---|---|
| 数据库 | 换 pgvector 镜像；新增记忆相关表（文档块索引、核心记忆条目、成员档案；迁移 0022–0028）。记忆表全部带 `project_id`；核心记忆条目额外预留组织级归属；成员档案表除外——随人走、不挂项目 |
| 后端 | 新增 memory 领域模块：索引任务、检索接口（带项目隔离 + 档案类型跨项目放行）、问答接口、文档版本管理、核心记忆的提议/确认/整合接口 |
| 文件模块 | 知识文档版本化（同名上传=新版本，不可删除）；白名单加 .docx |
| Worker | 新增两类异步任务：索引任务（读内容 → 切块 → 转向量 → 入库）；总结任务（任务结束后提炼经验 → 生成核心记忆提议） |
| Agent | 工具注册表加只读工具：检索项目文档、检索历史记录、查成员统计；上下文装配处注入核心记忆（按 run 的 project_id 过滤）；新增"提议记忆条目"能力（走现有建议审批） |
| 前端 | 新知识库页面（问答 + 依据列表）；文档版本历史查看；核心记忆的查看与确认入口 |
| 测试 | 纳入多项目测试接缝：复用双项目 fixture，补记忆数据的隔离/越权断言；成员档案跨项目可见作为例外单独断言 |
| 依赖 | pypdf（读 PDF）、python-docx（读 Word）；Ollama 拉取 qwen3-embedding 模型 |

## 14. 本期不做（明确排除）

- 图片 OCR / 扫描件识别
- 多轮对话、流式输出
- 混合检索（关键词+语义融合，后续优化项）
- 成员自评档案 + 确认流程
