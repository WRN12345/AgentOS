# 阶段 2：身份、成员与工作项

- 对应设计文档：第 20 章"阶段 2：身份、成员与工作项"，另涉及第 6、7、8、11、12、16、17 章。
- 阶段目标：实现本地账号登录与令牌体系、项目成员与能力管理、工作项状态机及命令 API，并落地统一错误格式、幂等键与审计基础设施。

## T2.1 统一 API 错误格式与 Idempotency-Key

- 状态：已完成

**目标**

按 17.1 节落地统一错误响应格式，并按第 12 章要求为所有状态变更接口支持 `Idempotency-Key`。

**具体内容**

- 在 `core/` 实现全局异常处理，统一输出 `{"code", "message", "request_id", "details"}` 结构（17.1 节示例），每个请求生成并透传 `request_id`。
- 实现 `Idempotency-Key` 中间件/依赖项：所有改变状态的接口（POST/PATCH 命令类）接受幂等键，重复请求返回第一次结果（17.2 节）。
- 幂等记录持久化（可用 Redis 或 PostgreSQL 表），键与操作者、接口路径关联，避免跨用户串用。
- 更新接口要求客户端携带版本号，版本冲突返回 HTTP 409 与错误码（如 `WORK_ITEM_VERSION_CONFLICT`），该约定在本任务定义、在 T2.6 正式启用。

**依赖**

T1.2

**验收标准**

- 业务异常与未捕获异常均按 17.1 节 JSON 结构返回，且包含 `request_id`。
- 集成测试：同一 `Idempotency-Key` 重复调用同一命令接口，只执行一次业务写入，第二次返回第一次的结果。

## T2.2 Argon2 密码与 Access/Refresh Token 登录

- 状态：已完成

**目标**

按 12.1 节实现登录、刷新、登出与当前用户查询，满足第 16 章密码与令牌安全要求。

**具体内容**

- 建表：`users`（账号、密码哈希、启用状态、令牌版本）与 `refresh_tokens`（Refresh Token 哈希、过期和撤销状态），见第 11 章。
- 密码使用 Argon2 哈希（16 节）；首版不开放公开注册，账号由项目负责人创建（16 节，创建入口在 T2.3）。
- 实现 `POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`GET /auth/me`（12.1 节）。
- Access Token 短期有效；Refresh Token 以哈希形式持久化、可撤销，登出即撤销；禁用用户或提升 `users` 令牌版本后旧令牌失效。
- `domains/identity` 承载全部逻辑，API 依赖项解析当前用户供后续所有接口使用。

**依赖**

T1.3、T2.1

**验收标准**

- 正确密码可登录并签发 Access/Refresh Token；错误密码、禁用用户登录按统一错误格式拒绝。
- 登出后原 Refresh Token 无法再次换取 Access Token。
- 数据库中不存在明文密码与明文 Refresh Token（仅哈希）。

## T2.3 项目成员与能力模型管理

- 状态：已完成

**目标**

按 6.1、6.2 节实现单项目配置、成员维护与能力标签管理，开放 12.2 节成员 API。

**具体内容**

- 建表：`projects`（单项目配置，首版只有一条有效项目记录）、`project_members`（项目角色、显示名、可投入时间、Git 用户名）、`member_capabilities`（能力标签、熟练度 1–5、负责人确认状态），见第 11 章。
- 实现 `GET /members`、`POST /members`、`PATCH /members/{id}`、`PUT /members/{id}/capabilities`（12.2 节）。
- 权限规则（6.1 节）：仅项目负责人可创建、禁用和维护成员；成员可填写自己的能力，负责人确认（6.2 节）。
- 项目内透明范围（6.1 节）：成员接口返回全员汇总工作量、当前工作状态所需的摘要字段；不暴露审核意见、令牌等隐私字段（16 节）。
- 每个 API 用例显式执行项目角色和资源关系校验（16 节），权限策略集中在应用服务层（4.1 节）。

**依赖**

T2.2

**验收标准**

- 普通成员调用 `POST /members` 返回 403；负责人可创建成员并同时生成初始账号。
- 成员提交能力后处于未确认状态，负责人确认后状态翻转，全程留痕可查询。
- `GET /members` 对任意项目成员返回全员摘要，且响应中不包含密码哈希、令牌等字段。

## T2.4 audit_events 追加式审计基础设施

- 状态：已完成

**目标**

按第 3 章原则 5 与第 16 章建立 `audit_events` 追加式事件写入能力，供所有业务模块复用。

**具体内容**

- 建表：`audit_events`（操作者、动作、目标、变更前后摘要、请求 ID、时间和来源 IP），见第 11、16 章。
- 提供 `domains/audit` 的写入服务：与业务状态变更在同一个数据库事务中写入（原则 5）；只提供追加接口，不提供修改和删除路径（第 11 章）。
- 事件来源 IP 与请求 ID 从请求上下文自动填充（依赖 T2.1 的 `request_id` 机制）。
- 提供只读查询能力，为 12.6 节 `GET /audit-events` 和阶段 6 审计测试（18.1 节）做准备；查询接口的开放权限在阶段 3/6 随页面完善，本任务至少保证负责人可查。

**依赖**

T1.3

**验收标准**

- 通过写入服务产生的审计事件包含操作者、动作、目标、请求 ID、时间和来源 IP 全部字段。
- 数据库层面无更新/删除审计事件的应用代码路径；审计测试可验证一次业务写入与事件落库同生共死（模拟事件写入失败时业务写入回滚）。

## T2.5 工作项数据模型与状态机

- 状态：已完成

**目标**

按 7.1 节建立工作项模型，并按 8.1 节实现状态机与乐观锁。

**具体内容**

- 建表：`work_items`（标题、说明、验收标准、优先级、当前负责人、DDL、状态、乐观锁 `version`）与 `work_item_collaborators`（协作者关系），见第 11 章。
- 在 `domains/work_items` 实现 8.1 节状态机：`DRAFT → READY → IN_PROGRESS → IN_REVIEW → COMPLETED`，含 `BLOCKED` 与 `CANCELLED` 分支，非法迁移一律拒绝。
- 主责任唯一约束（第 3 章原则 4）：一个工作项只有一名当前主执行人，协作者通过 `work_item_collaborators` 关联。
- 更新走乐观锁：客户端携带 `version`，不匹配返回 409（17.2 节，复用 T2.1 的错误格式）。
- 每次状态迁移同事务写入审计事件（复用 T2.4）。

**依赖**

T2.3、T2.4

**验收标准**

- 单元测试覆盖 8.1 节全部合法迁移与至少每个非法迁移分支（如 `DRAFT → IN_PROGRESS` 被拒）。
- 并发更新同一工作项时，后到请求收到 409 版本冲突。
- 每次状态变化均可在 `audit_events` 中查到对应事件。

## T2.6 工作项命令 API

- 状态：已完成

**目标**

按 12.3 节开放工作项查询与命令接口，落实角色权限。

**具体内容**

- 实现 `GET /work-items`（支持按负责人、状态、DDL 过滤，对应 13.1 节列表需求）、`POST /work-items`、`GET /work-items/{id}`、`PATCH /work-items/{id}`。
- 实现命令接口：`POST /work-items/{id}/start`、`/block`、`/unblock`、`/submit`、`/cancel`（12.3 节）；`submit` 仅将状态推进到 `IN_REVIEW`，交付物内容在阶段 4 接入。
- 权限规则（6.1 节）：仅项目负责人可创建、分配、取消工作项；主执行人可开始、阻塞、解除阻塞、提交；所有成员可查看全部工作项的标题、状态、负责人、优先级和截止时间（透明原则 6）。
- 所有命令接口支持 `Idempotency-Key`，更新接口要求版本号（T2.1）。
- 负责人变更历史可查：任何 `assignee_id` 变化都写入审计事件，为设计文档第 22 章标准 2"历史负责人完整可查"打底。

**依赖**

T2.5

**验收标准**

- 普通成员创建工作项返回 403；负责人创建并发布后，指定主执行人可 `start`。
- `GET /work-items` 对成员返回全量列表与摘要字段。
- 重复携带同一 `Idempotency-Key` 调用 `start` 只产生一次状态变化和一条审计事件。

## T2.7 前端登录、成员与工作项页面

- 状态：已完成

**目标**

按 13.1、13.2 节实现登录页及成员、工作项的核心页面，打通阶段 2 全部 API。

**具体内容**

- `features/auth`：登录页、令牌存储与刷新、未登录路由守卫（对接 12.1 节接口）。
- `features/members`：成员列表与能力维护页（对接 12.2 节接口），区分负责人与成员视角（负责人可编辑/确认，成员只读与填报自己的能力）。
- `features/work-items`：工作项列表（按负责人、状态、DDL 过滤）、详情页（状态徽标、负责人、优先级、DDL）、负责人创建工作项表单；命令操作（开始、阻塞、解除阻塞、提交、取消）按当前用户角色与状态显隐。
- `features/dashboard`：团队透明看板雏形——全员工作量、当前状态、任务数量和即将到期事项（13.2 节，对接 `GET /dashboard`，若该接口未就绪可先以 `GET /work-items` 聚合）。
- 全部写操作走 T1.5 的统一 API 客户端，携带 `Idempotency-Key` 与版本号，409 时提示刷新。

**依赖**

T2.2、T2.3、T2.6、T1.5

**验收标准**

- 成员可登录、查看团队看板与全部工作项，但看不到创建/分配/取消入口。
- 负责人可创建成员、确认能力、创建并分配工作项。
- 工作项详情页状态与实际后端状态一致，版本冲突时给出"任务已被其他成员更新，请刷新后重试"提示。
