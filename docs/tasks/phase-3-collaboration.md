# 阶段 3：动态协作

- 对应设计文档：第 20 章"阶段 3：动态协作"，另涉及第 4、7、8、11、12、17 章。
- 阶段目标：实现协作请求、主任务转派审批、DDL 变更及影响审批三条动态流转链路，并建立站内通知与 SSE 实时事件通道。

## T3.1 协作请求数据模型与状态机

- 状态：待开始

**目标**

按 7.2 节建立协作请求模型，并按 8.2 节实现状态机。

**具体内容**

- 建表：`collaboration_requests`（发起人、接收人、关联工作项、独立目标、模板、截止时间、产物回传内容、状态、`version`），见第 11 章。
- 在 `domains/collaboration` 实现 8.2 节状态机：`REQUESTED → ACCEPTED | DECLINED | CANCELLED`，`ACCEPTED → IN_PROGRESS → SUBMITTED → REVISION_REQUESTED | COMPLETED` 等全部迁移，非法迁移拒绝。
- 落实 7.2 节规则：协作请求不改变主任务负责人；产物回传给发起人并关联原工作项；发起协作请求不需要项目负责人事前审批（2.1 节）。
- 乐观锁与幂等键复用 T2.1 约定；每次状态迁移同事务写审计事件。

**依赖**

T2.5

**验收标准**

- 单元测试覆盖 8.2 节全部合法迁移与代表性非法迁移。
- 协作请求状态变化不影响 `work_items.assignee_id` 与工作项状态。
- 状态迁移均产生审计事件。

## T3.2 协作请求 API（接受/拒绝/提交/退回/完成）

- 状态：待开始

**目标**

按 12.4 节开放协作请求的发起与处理接口。

**具体内容**

- 实现 `POST /work-items/{id}/collaboration-requests`（发起，需为当前工作项负责人）、`POST /collaboration-requests/{id}/accept`、`/decline`、`/submit`、`/request-revision`、`/complete`（12.4 节）。
- 权限规则（6.1 节）：仅接收人可接受/拒绝/提交；仅发起人可要求修改、接受完成或取消。
- `submit` 携带回传产物（文本与关联信息；文件类产物在阶段 4 打通后可直接引用）。
- 所有命令接口支持 `Idempotency-Key` 与乐观锁版本号。

**依赖**

T3.1

**验收标准**

- 集成测试跑通"发起 → 接受 → 开始 → 提交 → 发起人接受完成"完整链路，以及拒绝、要求修改两条分支。
- 非接收人调用 `accept` 返回 403；重复幂等键请求不产生重复事件。

## T3.3 主任务转派申请与审批

- 状态：待开始

**目标**

按 7.3、8.3 节实现转派申请与负责人审批，审批通过时同事务更新负责人并留痕。

**具体内容**

- 建表：`transfer_requests`（当前负责人、建议新负责人、转派原因、对 DDL 和现有协作请求的影响、状态、`version`），见第 11 章；Agent 能力匹配建议字段预留关联 `agent_suggestions`（阶段 5 填充）。
- 实现 8.3 节状态机：`PENDING → APPROVED | REJECTED | CANCELLED`；同一工作项同时只能存在一个待审批的转派申请（8.3、17.2 节）。
- 实现 `POST /work-items/{id}/transfer-requests`、`POST /transfer-requests/{id}/approve`、`/reject`（12.4 节）；审批权仅项目负责人（6.1 节）。
- 审批通过时才在一个事务中更新 `work_items.assignee_id` 并写入审计事件（7.3 节）；审批前主任务负责人不变化。
- 审批接口使用幂等键，重复请求返回第一次结果（17.2 节）。

**依赖**

T2.6、T3.1

**验收标准**

- 存在待审批转派时，对同一工作项再次发起转派返回冲突错误。
- 审批通过后同一事务内 `assignee_id` 更新且审计事件落库；历史负责人可通过审计事件完整追溯（第 22 章标准 2）。
- 并发重复审批（相同/不同幂等键）只生效一次。

## T3.4 DDL 变更申请与影响审批

- 状态：待开始

**目标**

按 7.4、8.4 节实现 DDL 变更申请，正确区分协作级与主任务级审批。

**具体内容**

- 建表：`deadline_change_requests`（目标对象类型：协作请求或主工作项、原 DDL、新 DDL、影响分析结果、状态、`version`），见第 11 章。
- 实现 8.4 节状态机：`PENDING_IMPACT_ANALYSIS → PENDING_APPROVAL → APPROVED | REJECTED | CANCELLED`。
- 业务规则（7.4 节）：协作请求 DDL 变化不影响主任务 DDL 时由双方直接确认并留痕；影响主任务 DDL 时生成影响分析并提交项目负责人审批；主任务 DDL 的任何修改都必须负责人批准。
- 同一工作项只能有一个待审批主 DDL 变更（17.2 节）；审批通过同事务更新 DDL 并写审计。
- 影响分析先生成规则化结果（受影响协作请求与依赖列表）；AI 影响分析在阶段 5 接入，且分析失败不阻塞人工审批——界面显示"未生成 AI 影响分析"（8.4 节），本任务需预留该状态表达。
- 实现 `POST /work-items/{id}/deadline-change-requests`、`POST /deadline-change-requests/{id}/approve`、`/reject`（12.4 节）。

**依赖**

T2.6、T3.1

**验收标准**

- 协作级 DDL 变更无需负责人审批即可完成并留痕；主任务级变更未经负责人批准不生效。
- 审批通过后工作项 DDL 与审计事件同事务更新。
- 影响分析缺失（模拟失败）时审批流程仍可走完，状态与界面上有明确标识。

## T3.5 站内通知（notifications 表与查询/已读）

- 状态：待开始

**目标**

按 2.1 节"站内通知、待办中心"要求建立通知写入与查询能力。

**具体内容**

- 建表：`notifications`（接收人、类型、关联业务对象、正文、已读状态），见第 11 章。
- `domains/notifications` 提供写入服务，供工作项、协作、转派、DDL 各模块在关键事件时调用（与业务事件同事务或紧随其后，保证不丢）。
- 实现 `GET /notifications`、`POST /notifications/{id}/read`（12.6 节），以及 `GET /approvals`（负责人待审批事项聚合：转派、主任务 DDL 变更；12.6 节）。
- 通知正文只包含摘要信息，不包含审核意见等隐私内容（16 节）。

**依赖**

T2.4

**验收标准**

- 发起协作请求、提交转派申请、审批完成等关键事件均产生对应接收人的通知。
- 已读接口幂等；`GET /approvals` 仅对负责人返回待审批列表，普通成员为空。

## T3.6 SSE 实时事件流 /events/stream

- 状态：待开始

**目标**

按 4.3 节实现 `GET /events/stream`，向客户端推送实时事件；首版不做 WebSocket。

**具体内容**

- 实现 `GET /events/stream`（12.6 节）：基于 Server-Sent Events，按用户推送其相关事件。
- 事件类型覆盖 4.3 节清单中阶段 3 已具备的部分：任务状态变化、新协作请求、待审批事项、到期或逾期提醒（到期提醒由 Scheduler 扫描任务触发，复用 T1.6 调度挂点）。
- 通道层复用 Redis（pub/sub 或等价机制）做 API 进程内事件分发；断线重连与 `Last-Event-ID` 处理可按最小可用实现。
- 所有写操作仍走 REST，SSE 只读（4.3 节）。

**依赖**

T3.5

**验收标准**

- 用户 A 对工作项执行状态变更后，相关用户 B 的 SSE 连接在数秒内收到事件。
- 到期提醒扫描任务触发后，相关成员收到 SSE 事件与站内通知。
- 接口清单中无 WebSocket 端点。

## T3.7 前端协作、审批中心与待办页面

- 状态：待开始

**目标**

按 13.1、13.2 节实现协作请求、审批中心、待办中心与通知，并接入 SSE 实时刷新。

**具体内容**

- `features/work-items` 详情页补充协作区：发起协作请求、查看收到/发出的协作及状态操作（13.2 节"我的协作"）。
- `features/approvals`：负责人审批中心——转派申请、主任务 DDL 变更的审批卡片（通过/驳回，附影响信息；无 AI 影响分析时显示对应提示）；成员侧的转派与 DDL 变更申请表单（13.1、13.2 节）。
- 待处理中心：需要接受、提交、修改或确认的事项聚合（13.2 节"待处理"），对接 `GET /approvals` 与 `GET /notifications`。
- 通知入口与已读交互；接入 `GET /events/stream`，收到事件后失效对应 TanStack Query 缓存自动刷新。
- 项目时间线雏形：基于 `GET /audit-events` 展示关键事件流（13.1 节"项目时间线"）。

**依赖**

T3.2、T3.3、T3.4、T3.6

**验收标准**

- 成员可在页面完成"发起协作 → 对方接受 → 提交 → 完成"全流程，无需调用 API 工具。
- 负责人可在审批中心完成转派与主任务 DDL 审批，结果实时反映到列表与详情。
- 另一浏览器会话执行关键动作后，当前页面无需手动刷新即更新。
