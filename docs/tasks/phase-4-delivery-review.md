# 阶段 4：交付与审核

- 对应设计文档：第 20 章"阶段 4：交付与审核"，另涉及第 7、8、11、12、14、16 章。
- 阶段目标：实现 Git 链接、文本与本地文件三类交付物的版本化提交、文件安全存储与权限下载，以及负责人最终审核与完成归档。

## T4.1 StorageProvider 接口与 LocalStorageProvider

- 状态：已完成

**目标**

按第 14 章建立存储抽象，业务层只依赖 `StorageProvider` 接口。

**具体内容**

- 在 `infrastructure/storage/` 定义 `StorageProvider` 接口（写入、读取、删除、存在性检查等最小集合），实现 `LocalStorageProvider`（MVP），`S3StorageProvider` 仅保留接口演进空间不实现（14 章）。
- 文件写入配置的本地根目录（`data/uploads/`）；数据库仅保存相对 `storage_key`，不保存宿主机绝对路径（14 章）。
- 配置项（存储根目录、大小上限、允许扩展名与 MIME 类型白名单）纳入 T1.2 的配置模块。
- 明确禁止直接暴露上传目录：静态服务/反向代理不得映射 `data/uploads/`（14 章）。

**依赖**

T1.2

**验收标准**

- 单元测试通过 `StorageProvider` 接口注入 `LocalStorageProvider` 完成写入/读取/删除。
- 业务层代码（grep 验证）不直接引用文件系统路径或具体 Provider 实现。

## T4.2 文件上传流程与 stored_files 落库

- 状态：已完成

**目标**

按第 14 章上传流程实现 `POST /files`，保证校验、哈希与落库的一致性。

**具体内容**

- 建表：`stored_files`（存储后端、相对 `storage_key`、大小、类型、SHA-256 哈希、上传人、关联业务对象），见第 11 章。
- 实现 `POST /files`（12.5 节），严格按 14 章流程：1) 流式写入临时文件；2) 校验大小、扩展名和 MIME 类型；3) 计算 SHA-256；4) 原子移动到正式目录；5) 写入 `stored_files` 与审计事件。
- 补偿清理：文件最终落盘与数据库记录失败时执行补偿，删除已落盘文件（17.2 节）。
- 上传接口要求登录态，限流/大小限制按配置执行。

**依赖**

T4.1、T2.4

**验收标准**

- 合法文件上传后，`stored_files` 记录存在、磁盘文件 SHA-256 与库中哈希一致。
- 超限大小或非法类型文件被 4xx 拒绝且磁盘无残留。
- 模拟数据库写入失败时，已落盘文件被补偿删除。

## T4.3 文件下载权限检查

- 状态：已完成

**目标**

按第 16 章实现 `GET /files/{id}/download`，所有下载必须经过权限校验。

**具体内容**

- 实现 `GET /files/{id}/download`（12.5 节）：通过 FastAPI 鉴权后由后端流式返回文件，不直接暴露上传目录（14 章）。
- 权限规则（16 节）：验证当前用户是否与文件关联工作项有关（主执行人、协作者、协作请求相关人）；项目负责人可查看全部文件；无关成员拒绝下载。
- 下载行为写入审计事件（操作者、目标文件、请求 ID、来源 IP）。
- 响应头设置正确的文件名与 Content-Type；文件不存在或已清理时按统一错误格式返回。

**依赖**

T4.2、T2.3

**验收标准**

- 与工作项无关的成员下载返回 403，负责人与工作项相关成员可正常下载。
- 直接猜测 `storage_key` 路径无法绕过 API 访问文件。
- 下载动作在 `audit_events` 可查（第 22 章标准 13 的技术支撑）。

## T4.4 交付物版本化（Git 链接/文本/文件）

- 状态：已完成

**目标**

按 7.5 节实现三类交付物的版本化提交，重提不覆盖旧版本。

**具体内容**

- 建表：`deliverables`（工作项、类型：Git 链接/文本/文件、内容或 `stored_files` 引用、版本号、提交人、提交时间），见第 11 章；文件版本、哈希、提交人、提交时间和关联任务留痕（2.1 节）。
- 实现 `POST /work-items/{id}/deliverables`（12.5 节）：每次提交生成新版本，版本号递增，旧版本保留可查（7.5 节）。
- 与 `POST /work-items/{id}/submit`（T2.6）打通：提交审核时必须存在当前版本交付物；协作请求的产物回传也可引用交付物/文件。
- 权限：仅当前主执行人（或协作请求接收人对应回传场景）可提交；提交动作写审计。

**依赖**

T4.2、T2.6

**验收标准**

- 同一工作项连续提交三次交付物，产生版本 1/2/3 且历史版本内容均可查询。
- 无交付物时调用 `submit` 被拒绝并提示先提交交付物。
- 文件类交付物可追溯到 `stored_files` 的哈希记录。

## T4.5 最终审核与 reviews 留痕

- 状态：已完成

**目标**

按 7.5 节实现负责人最终审核，完成 8.1 节 `IN_REVIEW` 状态分支闭环。

**具体内容**

- 建表：`reviews`（工作项、关联交付物版本、结论、反馈、审核人、时间），见第 11 章。
- 实现 `POST /work-items/{id}/reviews`（12.5 节），支持三种结论（7.5 节）：通过并完成工作项（`IN_REVIEW → COMPLETED`）、要求修改并填写反馈（`IN_REVIEW → IN_PROGRESS`）、拒绝当前交付但保持工作项继续执行。
- 权限：仅项目负责人可审核（6.1 节）；接口支持幂等键，状态推进与 `reviews` 记录、审计事件同事务写入。
- 审核意见属于隐私信息：仅负责人与相关工作项责任人可见，不进入全员透明范围（16 节、原则 6）。

**依赖**

T4.4

**验收标准**

- 三种审核结论分别驱动正确的状态机迁移，且 `reviews` 记录与审计事件同事务落库。
- 普通成员调用审核接口返回 403；无关成员无法通过 API 读取审核反馈正文。
- 通过后工作项进入 `COMPLETED` 且不可再提交新交付物版本。

## T4.6 前端提交交付与审核界面

- 状态：已完成

**目标**

按 13.1、13.2 节实现交付物提交、版本历史与负责人审核的完整界面。

**具体内容**

- `features/deliverables`：任务详情页"提交交付"区——Git 链接、文本说明、文件上传三种形式（13.2 节），展示版本历史、哈希、提交人与时间。
- 文件上传组件：进度反馈、大小/类型前置校验、失败后重试（对接 `POST /files`）。
- `features/approvals` 补充最终审核卡片：查看当前交付物版本、选择通过/要求修改/拒绝并填写反馈（13.1 节审批中心）。
- 下载入口按权限显隐，403 时给出明确提示；文件处理完成等 SSE 事件触发列表刷新（4.3 节）。

**依赖**

T4.4、T4.5、T3.6

**验收标准**

- 成员可在页面完成三类交付物提交并看到版本历史递增。
- 负责人可在审批中心查看交付物并完成三种审核操作，状态变化实时可见。
- 无关成员看不到下载入口，直接访问下载链接返回 403 提示。
